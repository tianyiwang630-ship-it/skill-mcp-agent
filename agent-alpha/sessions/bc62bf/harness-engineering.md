# Harness Engineering：AI Agent 时代的工程新范式

> **核心理念：Agent = Model + Harness**
> 模型是引擎，Harness 是底盘、刹车、方向盘和仪表盘。没有 Harness，再强大的引擎也无法安全承载乘客。

---

## 一、什么是 Harness Engineering？

### 1.1 概念的诞生

Harness Engineering 是 AI Agent 时代兴起的一个新兴工程学科。它指的是：**除了模型本身之外，所有用来约束、引导、控制和验证模型行为的代码、配置和运行时基础设施的整体设计**。

这个概念随着 AI Agent 在生产环境中的大规模应用而逐渐浮出水面。2025 年，业界发现了一个痛苦的现实：几乎每个团队的 Agent 在 demo 中表现惊艳，但一进入生产环境就问题百出——进入死循环、调用错误的 API、烧掉巨额预算、产出毫无价值的输出。深入分析后发现，**问题几乎都不在模型本身，而在包裹模型的 Harness 缺失或不成熟**。

### 1.2 核心比喻

业界为这个概念提供了多个生动的比喻：

- **缰绳与马**：LLM 是一匹马力强大的马，有巨大的原始能力，但没有方向感、不懂边界、不知道何时停止。Harness 就是缰绳、鞍座和笼头，把原始力量引导为可控、有用的工作。
- **CPU 与操作系统**：Hugging Face 的 Phil Schmid 提出了另一个经典比喻——模型是 CPU，Harness 是操作系统。CPU 执行指令，但 OS 管理内存、调度进程、处理 I/O、强制权限、恢复崩溃。CPU 没有 OS 只是一个发热元件；模型没有 Harness 只是一个演示品。
- **框架 vs 工厂**：Framework（框架，如 LangChain）是蓝图和建筑材料；Harness 是工厂车间——管理 Agent 如何执行、每步收到什么上下文、工具调用如何验证、步骤失败时怎么办、什么时候需要人类介入。

### 1.3 一个真实的失败案例

> 去年我参与的一个团队部署了一个在所有演示中碾压全场的 Agent。它回答复杂问题、正确顺序调用工具，给每个利益相关者都留下了深刻印象。然后它进了生产环境。在某个周二凌晨 3 点，这个同样的 Agent 进入了一个针对不稳定 API 的重试循环，烧掉了 400 美元的 API 调用费用，产出了毫无用处的结果。模型没问题。提示词没问题。**包裹模型的 agent harness，根本就没有以任何有意义的形式存在。**

## 二、核心组成部分

一个完整的 Agent Harness 通常包含六大核心组件。根据 [harness-engineering.ai](https://harness-engineering.ai/blog/agent-harness-complete-guide/) 的框架，这六大组件组织为两层：基础层（上下文工程、工具编排、状态管理）和安全层（验证与安全、人机协作、生命周期管理）。

### 2.1 Context Engineering（上下文工程）

**定义**：决定模型在每个执行步骤中能看到什么信息。

这比传统的"提示工程"范围更广，涵盖了完整输入管道：系统提示词、检索到的文档、对话历史、工具执行结果和环境状态。

**核心挑战**：上下文窗口是有限的。当 Agent 执行到第 50 步时，早期的关键信息可能已被无关的工具输出、错误消息和中间结果挤出窗口。上下文工程必须主动管理"什么保留、什么压缩、什么丢弃"。

**关键设计**：

- OpenAI 的 Codex 使用机器可读的 artifacts（架构约束文档、API 契约、设计决策记录）来保持模型在数百步执行中的专注度
- Anthropic 的 `claude-progress.txt` 模式——Agent 维护一个结构化的便签本，记录已完成步骤、当前阻塞点、架构决策和下一步行动

### 2.2 Tool Orchestration（工具编排）

**定义**：管理模型在每个步骤可以使用哪些工具，以及如何处理工具的执行。包括工具选择、参数验证、执行沙箱化、超时管理和错误处理。

**核心设计原则——动态工具作用域 (Dynamic Tool Scoping)**：

> Vercel 在构建 v0 编码 Agent 时发现：移除 80% 的可用工具后，效果反而显著提升。工具太多 = 更多困惑 + 更多错误选择 + 更多失败任务。

正确做法是根据当前任务阶段动态暴露工具集：

| 任务阶段 | 应该暴露的工具 |
|---------|--------------|
| 规划步骤 | 无需文件系统写权限 |
| 代码执行步骤 | 无需网络搜索 |
| 调试步骤 | 日志查看器、调试工具 |

### 2.3 State & Memory Management（状态与记忆管理）

**定义**：Agent 如果要运行几分钟到几小时，必须有持久化状态。

**两个关键能力**：

1. **Checkpoint-Resume（检查点恢复）**：如果 Harness 在任务中途崩溃，能否从断点恢复而不是从头开始？**这对生产 Agent 来说不是可选项，而是基础项。**
2. **跨会话记忆**：Agent 第二天回来还记得什么？记忆如何结构化？

**经典方案**：

- **进度文件模式**（Anthropic）：Agent 维护一个 `claude-progress.txt` 文件，记录已完成步骤、当前阻塞点、架构决策、下一步行动。下一个会话从这个文件 + Git 历史中获取压缩的相关摘要
- 类比：像医院交接班一样处理 Agent 会话——结构化交接、明确状态、清晰下一步

### 2.4 Verification & Safety（验证与安全）

**这是单个最高影响力的模式。**

在 Agent 提交代码、发送消息或采取任何不可逆行动之前，添加验证步骤：

```
Agent 生成输出 → 验证层评估是否符合预期标准 → 通过则继续 / 失败则重试或升级
```

**真实数据**：团队报告添加结构化验证后，任务完成率从 **83% 提升到 96%**——模型本身没有任何改变。

**验证类型**：

| 类型 | 计算型（Computational） | 推理型（Inferential） |
|------|----------------------|---------------------|
| 性质 | 确定性、快速 | 语义分析、AI 评判 |
| 运行 | CPU | GPU/NPU |
| 例子 | 测试、Linter、类型检查、结构分析 | AI 代码审查、"LLM as Judge" |
| 成本 | 毫秒级，便宜 | 秒~分钟级，贵 |
| 可靠性 | 确定性 | 概率性 |

### 2.5 Human-in-the-Loop Controls（人机协作控制）

**定义**：不是所有 Agent 行动都应该是自主的。Harness 需要为高风险操作设置审批门。

**需要审批的高风险操作**：

- 删除数据
- 发送外部通信
- 金融交易
- 修改基础设施

**设计挑战**：审批门太多 → Agent 比手动做还慢；审批门太少 → 一个幻觉 API 调用就能制造生产事故。

**最佳实践**：从严格的审批要求开始，随着团队对特定类别建立信心，逐步放宽限制。

### 2.6 Lifecycle Management（生命周期管理）

**定义**：涵盖 Agent 启动、健康监控、优雅关闭、崩溃恢复的完整管理。

| 能力 | 说明 |
|------|------|
| 健康检查 | Agent 是否还在进展中，还是卡在循环里？ |
| 资源限制 | 每个任务最大 Token 数、最大 wall-clock 时间 |
| 优雅关闭 | 保存状态、释放资源、报告最终状态 |
| 崩溃恢复 | 检测失败、加载检查点、带退避的重启 |

## 三、Martin Fowler 的 Harness 分类框架

Thoughtworks 的 Birgitta Böckeler 在 [Martin Fowler 博客](https://martinfowler.com/articles/harness-engineering.html)上发表的文章对 Harness 做了更精细的分类，引入了控制论的思想：

### 3.1 Feedforward vs Feedback 控制

| 类型 | 作用机制 | 目的 |
|------|---------|------|
| **Guides（引导）** | 预测 Agent 行为，在**它行动之前**进行引导 | 增加 Agent 第一次就做好的概率 |
| **Sensors（传感）** | 观察 Agent **行动之后**的结果 | 帮助 Agent 自我纠正 |

两者缺一不可：

- 只有 Feedback → Agent 重复同样的错误
- 只有 Feedforward → Agent 编码了规则但永远不知道是否有效

**特别有效的传感设计**：输出专门为 LLM 消费优化的信号，例如包含自我纠正指令的自定义 Linter 消息——这是一种正向的"提示注入"。

### 3.2 三类 Harness

#### 3.2.1 Maintainability Harness（可维护性约束）

调节内部代码质量和可维护性。这是**当前最容易实现的**类型，因为有大量现成的工具可以使用：

- **计算型传感**：可靠地捕获结构性问题——代码重复、圈复杂度、测试覆盖缺失、架构漂移、风格违规。便宜、成熟、确定性。
- **推理型传感**：部分处理语义问题——语义重复的代码、冗余测试、蛮力修复、过度工程。但成本高、概率性，不能每次提交都运行。
- **传感难以覆盖的问题**：问题诊断错误、过度工程和不需要的功能、对指令的误解。这些更高影响的问题，计算型和推理型传感器都不能可靠地捕获。

#### 3.2.2 Architecture Fitness Harness（架构健康约束）

定义和检查应用的架构特性，本质上是 Fitness Functions（适合度函数）。

示例：

- 技能前馈性能要求 + 性能测试反馈
- 日志标准指南 + 调试反思指令（要求 Agent 反思其可用的日志质量）

#### 3.2.3 Behaviour Harness（行为约束）

这是最难的部分——如何引导和感知应用功能行为是否符合预期。

目前大多数高自主性 Agent 的做法：

- **前馈**：功能规范（从简短提示到多文件描述）
- **反馈**：AI 生成测试套件是否通过，覆盖率是否足够，部分团队还用突变测试监控质量

**核心问题**：这种做法对 AI 生成测试的质量有太多信任，目前还不够可靠。"Approved Fixtures" 模式是一个有前景的探索方向（在某些适用场景选择性使用，而非全面解决方案）。

### 3.3 时机原则：Keep Quality Left

持续集成的团队始终面临如何根据成本、速度和关键性在不同开发阶段分布测试、检查和人工审查的挑战。Harness 中的反馈传感（包括推理型传感）需要相应地分布在生命周期中：

**前馈和反馈在变更生命周期中的分布**：

1. **集成前甚至提交前运行**（便宜、快速）：例如 Linter、快速测试套件、基本代码审查 Agent
2. **集成后在流水线中运行**（更贵，额外重复快速检查）：例如突变测试、更广泛的代码审查
3. **持续漂移和健康传感**（在变更生命周期之外持续运行）：例如死代码检测、测试覆盖质量分析、依赖扫描
4. **运行时反馈**：例如让 Agent 监控 SLO 退化并提出改进建议，或用 AI Judge 持续采样响应质量并标记日志异常

### 3.4 Harnessability（可约束性）

**不是所有代码库都同样容易被 Harness**。强类型语言天然拥有类型检查作为传感；定义清晰的模块边界提供了架构约束规则的发挥空间；Spring 这样的框架抽象掉了 Agent 甚至不需要担心的细节，无形中提高了 Agent 成功的机会。

这在 greenfield（新项目）vs legacy（遗留系统）中的表现截然不同：

- **Greenfield 团队**：可以从第一天起就将 Harness 性纳入考量——技术决策和架构选择决定了代码库未来有多可控
- **Legacy 团队**：尤其是技术债务积累严重的应用，面临更难的问题——**Harness 最需要的地方，也是最难构建的地方**

### 3.5 Harness Templates（约束模板）

大多数企业有几套覆盖 80% 需求的常见服务拓扑——暴露 API 的业务服务、事件处理服务、数据仪表板。在许多成熟的工程组织中，这些拓扑已经编码在服务模板中。

未来这些可能演变为 **Harness Templates**：一组约束和传感的捆绑，将编码 Agent 限制在特定拓扑的结构、约定和技术栈中。

挑战：一旦团队实例化模板，它们就开始与上游改进失去同步。Harness 模板将面临与微服务模板相同版本控制和贡献问题，而且可能更严重——推理型传感的非确定性使得它们比确定性工具更难测试。

### 3.6 人类工程师的角色

> 人类开发者凭借技能和经验，对每个代码库都携带着隐式的 Harness。我们吸收了约定和良好实践，我们感受过复杂的认知痛苦，我们知道我们的名字会出现在 commit 记录中。我们还携带组织对齐——对团队试图实现什么的认知，哪些技术债务因为业务原因被容忍，"好"在这个特定上下文中的含义。

**Agent 缺乏这一切**：没有社会责任感、对 300 行函数的本能厌恶、"我们这里不这样做" 的直觉，也没有组织记忆。

Harness 是试图将人类开发者经验外部化和显式化的尝试，但它只能走到这一步。构建一套连贯的 Guides + Sensors + 自我纠正循环是昂贵的，所以我们必须以明确的目标为导向进行优先排序：**一个好的 Harness 不一定旨在完全消除人类输入，而是将人类输入引导到最需要的地方。**

## 四、精妙的设计与最佳实践

### 4.1 渐进式上下文暴露（Anthropic / OpenAI）

不要给 Agent 一个巨大的 AGENTS.md 文件。OpenAI 的教训：

> 一个巨大的指令文件会挤掉任务、代码和相关文档——Agent 要么错过关键约束条件，要么开始针对错误的约束条件进行优化。过多的指导反而**失效**。当一切都"重要"时，一切都不重要了。

**正确方案**：让 AGENTS.md 像一个**地图**（而非 1000 页说明书）：

```
AGENTS.md（~100行，指向型目录）
├── ARCHITECTURE.md（顶层架构图）
├── docs/（分类索引的知识库）
│   ├── design-docs/（设计文档）
│   ├── exec-plans/（执行计划，含进度日志）
│   └── references/（参考文档）
├── DESIGN.md
├── FRONTEND.md
├── PLANS.md
├── PRODUCT_SENSE.md
└── SECURITY.md
```

LangChain 称之为"渐进式曝光"：Agent 从一个小的稳定切入点开始，被引导下一步该去哪里查看，而不是一开始就被淹没。

**关键实践**：Linter 和 CI 作业验证知识库的新状态是否已交叉链接且结构正确；一个定期运行的"doc-gardening" Agent 扫描那些不再反映真实代码行为的过时或废弃文档，并发起修复 PR。

### 4.2 Generator + Evaluator 双 Agent 结构（Anthropic）

Anthropic 在前端设计和长程编码任务中采用了 **GAN 风格的 Generator-Evaluator 双 Agent 架构**（灵感来自生成对抗网络）：

```
Planner Agent → Generator Agent → Evaluator Agent → (loop)
```

- **Planner Agent**：将一行需求扩展为完整的产品规范和任务分解
- **Generator Agent**：执行实现
- **Evaluator Agent**：根据具体可测量的标准对输出进行评分（将主观评价如"这个设计好吗？"转化为具体可评分的指标）

**Evaluator 的设计难度**：构建一个能可靠评分的 Evaluator 本身就是一项挑战。"什么构成好的设计？"这类问题需要先开发出一套标准，将主观判断转化为可量化评估的维度。

### 4.3 架构约束 + Linter 强制执行（OpenAI）

OpenAI 的 Codex 项目用五个月时间构建并交付了一款软件产品的内部 beta 版，**整个过程中没有一行代码是人工编写的**。他们使用自定义 Linter 和结构测试来强制执行架构边界：

**核心设计**：

- 每个业务域（如"应用设置"）中的代码只能"向前"依赖一组固定的层：`Types → Config → Repo → Service → Runtime → UI`
- 跨领域关注点（认证、连接器、遥测）通过单一的显式接口 `Providers` 接入
- 其他任何依赖都不被允许，通过自定义 Linter 和结构测试自动化强制执行

> 这种架构通常被认为需要数百名工程师才能推进。对于编码 Agent 来说，这是一个**先决条件**：有了约束，速度才不会下降，架构才不会漂移。

### 4.4 Self-Verification 自我验证循环（LangChain）

LangChain 提出的核心执行模式：

1. Agent 编写应用代码
2. 运行测试
3. 检查日志
4. 观察结果
5. 发现错误
6. 自动修复

**关键洞察**：工具（浏览器、日志、截图、测试运行器）给 Agent 提供了观察和分析工作的手段，形成了**自我验证闭环**。

LangChain 还发现：

- **文件系统是 Agent 的工作空间**：Agent 可以在此读取数据、代码和文档；可以增量添加和卸载信息而无需将所有内容塞入上下文；多个 Agent 和人类可以通过共享文件协调
- **Bash + 代码执行 = 通用工具**：与其为每个可能的操作构建工具，不如给 Agent 一个通用工具（Bash），让模型通过编写和执行代码来自主解决问题

### 4.5 Ralph Wiggum 循环（OpenAI）

OpenAI 的团队使用一个持续迭代模式（内部戏称为"Ralph Wiggum 循环"）：

```
Codex 打开 PR → 自动运行相关 Linter → 对人类/Agent 反馈做出响应 → 循环往复 → 直到所有 Agent 审查员满意
```

Codex 直接使用团队的标准开发工具（gh、Git、嵌入代码库的技术）来收集上下文，无需人工将上下文复制粘贴到 CLI 中。

### 4.6 上下文旋转 (Context Rot) 应对

**问题**：长程任务中，Agent 的上下文积累噪音、无关的工具输出、过时的决策，直到模型无法识别当前什么重要。症状包括：

- Agent 重复解决已经解决过的问题
- 与自己之前的决策矛盾
- 失去对原始任务目标的追踪

**Anthropic 的解决方案——双 Agent 模式**：

- **初始化 Agent**：在每个会话开始时新鲜运行，分析代码库当前状态和任务需求，为工作 Agent 构建干净的上下文
- **工作 Agent**：在清理后的上下文中执行

这就像医院交接班——接班的工程师不需要阅读过去 8 小时的所有消息，他们拿到的是一份结构化的交接简报。

### 4.7 黄金原则 + 自动循环清理（OpenAI）

OpenAI 团队发现 Codex 会复制代码库中已存在的模式（包括不健康或不合理的模式），导致随时间漂移。他们的解决：

1. 将"黄金原则"直接编码到代码库中（带有主观意见的机械规则，旨在保持代码库的可读性和一致性）：
   - 使用类型化的 SDK 而非临时命令
   - 不使用"YOLO 模式"探测数据——必须验证边界或依赖类型化 SDK
2. 建立循环清理流程：定期运行后台 Codex 任务，扫描偏差、更新质量等级，发起有针对性的重构 PR
3. 大多数重构 PR 在一分钟内完成审核并自动合并

> "技术债务就像一笔高息贷款：不断以小额定投偿还债务，总比让债务不断累积、最后痛苦地一次性解决要好得多。"

## 五、可靠性数学：为什么 Harness 如此重要？

**一个简单的计算揭示了为什么 Harness 不可或缺：**

假设多步 Agent 管道中每个步骤成功率为 95%。链接 20 个步骤：

```
0.95^20 = 35.8%
```

**这就是为什么团队报告"Agent 95% 成功率"但实际完成真实复杂任务时失败率高达三分之一的原因。**

```
任务完成率
│
│                    ████
│                ████
│            ████         ████ (添加验证后 96%)
│        ████                     ████
│    ████
│████
│
└──────────────────────────────────────→
   步骤1   步骤5   步骤10  步骤15   步骤20
            ↑               ↑
         95%^5           95%^20
         =77%            =36%
```

**这就是 Harness 存在的意义**：验证循环、重试策略（带退避）和检查点恢复把这 36% 推回到可接受的水平。

## 七、构建实践路径

根据 [harness-engineering.ai](https://harness-engineering.ai/blog/agent-harness-complete-guide/) 提供的框架：

| 阶段 | 行动 | 说明 |
|------|------|------|
| **Phase 1** | 添加验证循环 | 在 Agent 提交代码、发送消息或采取任何不可逆行动之前添加验证步骤。这是**最高可靠性投入产出比**的单项措施 |
| **Phase 2** | 添加状态持久化 | 每步成功后序列化 Agent 状态到持久存储。崩溃时从最后一个检查点重启。这可将失败时的 Token 成本**降低 30-50%** |
| **Phase 3** | 添加可观测性 | 为每个工具调用、模型调用和决策点添加执行追踪。跟踪 Token 使用量、wall-clock 时间和每个任务的成本 |
| **Phase 4** | 添加人机协作控制 | 识别哪些 Agent 行动带有现实风险并添加审批门。从保守审批开始，随着对 Agent 特定类别行为的信心增强逐步放宽 |

**关键警告**：构建生产级 Harness 需要数月，而非数周。Martin Fowler 的团队记录了这个现实——Harness 工程的工作量通常**大于 Agent 逻辑本身**。

## 八、Harness vs Context Engineering

**关系**：Context Engineering 是 Harness Engineering 的一个子集。

```
Harness Engineering
├── Context Engineering    ← 管理模型看到什么
├── Tool Orchestration     ← 管理模型能做什么
├── State Management        ← 管理跨会话状态
├── Verification & Safety   ← 管理输出质量
├── Human-in-the-Loop      ← 管理人类介入
└── Lifecycle Management   ← 管理运行生命周期
```

---

## 九、框架与 Harness 的区别

| 维度 | Framework（框架） | Harness（约束系统） |
|------|-----------------|-------------------|
| 定位 | 构建时的组件库 | 运行时执行环境 |
| 目的 | 组装 Agent 架构 | 在生产中govern Agent 行为 |
| 例子 | LangChain、CrewAI、AutoGen | Claude Agent SDK、Codex harness |
| 使用者 | 构建 Agent 的开发者 | 管理运行中 Agent 的基础设施 |
| 关键时机 | 设计和实现阶段 | 部署和运营阶段 |

**你通常两者都需要**：用框架构建 Agent，用 Harness 运行它。但大多数团队跳过了 Harness——将框架构建的 Agent 直接部署到生产环境中，没有使其可靠的运行时基础设施。这就是失败开始的地方。

## 十、未来趋势与开放问题

### 10.1 当前尚待解决的问题

- **Behaviour Harness**：如何在功能行为层面建立足够强的 Harness，使我们有信心减少监督和人工测试？
- **Harness 一致性**：如何随着 Harness 增长保持 Guides 和 Sensors 同步，不互相矛盾？
- **传感器有效性评估**：如果传感器从不触发，这代表高质量还是检测机制不足？我们需要一种评估 Harness 覆盖率和质量的方法（类似于代码覆盖率或突变测试对测试的作用）
- **人与 Agent 的判断分歧**：当指令和反馈信号指向不同方向时，如何信任 Agent 进行合理的权衡？
- ** Harness 治理**：反馈传感目前分散在交付步骤中，有真正的潜力开发工具来帮助配置、同步和系统化地推理它们

### 10.2 模型进化与 Harness 的关系

> 随着模型能力的提升，在某些情况下围绕模型的外围支架变得不那么重要——开发者可以等待下一个模型，看看某些问题是否自我解决。但另一方面，模型越好，就越有空间开发能够在模型基线能力之外实现复杂任务的 Harness。

Anthropic 的结论：**有趣 Harness 组合的空间不会随着模型改进而缩小。相反，它在移动。AI 工程师的持续工作就是不断找到下一个新颖的组合。**

## 十一、总结

**Harness Engineering 的本质**，是将"监控 AI"转变为"与 AI 协作"。它的核心哲学是：**控制不是限制，而是赋能**。

### 核心要点

1. **Agent = Model + Harness**：模型提供智力，Harness 使智力变得有用。模型是可以更换的组件；Harness 是产品本身
2. **可靠性差距来自 Harness**：两个使用相同模型的团队可能看到 60% vs 98% 的任务完成率差异——差距完全由 Harness 质量决定
3. **验证循环是最高杠杆**：添加结构化验证可将任务完成率从 83% 提升到 96%，无需改变模型
4. **控制策略需要平衡**：Feedforward + Feedback，计算型 + 推理型，自动化验证 + 人工审批
5. **构建生产 Harness 需要月级投入**：这不是配置工作，而是与构建数据库或操作系统调度器同等规模的基础设施工程

### 核心公式

```
可靠 Agent = Model + (Context + Tools + State + Verification + Human-in-Loop + Lifecycle)
```

**在 2026 年，不投资 Harness 的团队正在用最强大的引擎制造最不安全的汽车。**
